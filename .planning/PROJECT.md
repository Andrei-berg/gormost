# PROJECT.md — Gormost: Описание продукта

## Что это

Gormost — система управления работами Лефортовского тоннеля (ГБУ «Горьмост»).
Заменяет бумажные наряды и WhatsApp-чаты: диспетчер видит всё на экране, каждая служба работает в своей панели.

Помимо оперативных заявок (`requests`) система теперь охватывает:
- **План работ** — согласование план-нарядов службами по цепочке (нач. службы → гл. инженер → зам → босс → мастер), формирование бригад пофамильно
- **Смены и графики** — 4 сменные бригады (сутки через трое) + 6 типов графиков (1/3, 5/2, 3/3, 6/6, 15/15), два эталона расписания (`SHIFT_HOURS`, `SCHEDULES`)
- **HR-модуль** (`/hr`) — состав смены, статусы присутствия (append-only лог), приём/увольнение, табель Т-13, отчёты за период, экспорт (докладная, строевая записка, 1С)
- **Наряд-допуск** — конструктор наряда-допуска с каталогом видов работ по службам и живым бланком A4, классификатор работ повышенной опасности (п.15)
- **Журнал/планировщик** (`/journal`) — суточный план объект × служба × смена, публикация смены в read-only «План дня», запуск наряда-допуска
- **Срочные поручения** — единый механизм «срочное поручение сверху» (переформирование бригад, судьба плана)
- **ТБиОТ** (`/safety`) — модуль удостоверений/аттестаций

Полное описание архитектуры, потоков и файлов — в `CLAUDE.md` (актуальнее этого документа по деталям реализации).

**Repo:** https://github.com/Andrei-berg/gormost

## Current Milestone: v3.0 Планировщик-агент

**Goal:** ADMIN обучает агента словарю участка (локации, конструктивы, виды работ, чья служба, синонимы) из Титула/Конструктива/Годового плана; после этого диспетчер/мастер надиктовывает или вставляет текст работ, а агент раскладывает его в черновики плана день/ночь, разбитые по службам, — человек проверяет и публикует.

**Target features:**
- База знаний агента — каталог участка Гормост-Лефортово (транспортные тоннели ЛТР + Шереметьевский/Митьковский/Нижегородский, пешеходные тоннели ТТК участка, ЗБ ЛТР/ГТР, мосты участка), засеянный из xls Титула/Конструктива/Годового плана: объекты (инв.№, адрес, площади), конструктивные элементы (вид отделки + S), словарь видов работ с привязкой к службе, ед.изм., типовым периодом и составом
- Таблица синонимов/алиасов — «борт. камень» = «БК», «ЭВ №3» = «аварийный выход 3», «тт №3 КТР» → канонический объект
- Инструмент обучения (ADMIN) — постоянный: загрузка xls → классификация → staging → предпросмотр-диф → подтверждение в каталог; ручное и голосовое добавление сущностей; ведение алиасов; обучение на исправлениях разбора; очередь разборов с низкой уверенностью
- Агент-раскладчик — «🎤 Надиктовать план» в `/journal` и `/dispatcher`: голос (запись → расшифровка) или вставленный текст → предложение из N строк {объект, служба, работа, период, кол-во людей/техники, уверенность, исходная фраза}, многослужебная диктовка разбивается по службам → правка в предпросмотре → «Создать черновики» пишет `daily_plan_items` (неопубликованные)
- Провайдер-независимый AI-слой — один интерфейс (`extractPlan`, `transcribe`), адаптеры под любой LLM/STT (Anthropic, OpenAI, YandexGPT/GigaChat, self-hosted), выбор через env/конфиг без изменения кода; ограждения (агент только предлагает, не выдумывает сущности, пороги уверенности, лог разборов) — над адаптером, от провайдера не зависят

**Позже (не в этой вехе):** годовой план-график с помесячным контролем, материалы и нормы, автосоздание заявок/план-нарядов, объёмы/нормо-часы, весь реестр (фонтаны, памятники, набережные, Кремль).

## Жизненный цикл заявки

```
[HEAD создаёт заявку]
        ↓
      NEW
        ↓ HEAD нажимает "Согласовать" → approved_by_head = userId
        ↓
  ZAMPORAB видит заявку
        ↓ ZAMPORAB нажимает "Согласовать" → approved_by_zamporab = true
        ↓
    PLANNED  ← Диспетчер видит заявку (канбан/таблица)
        ↓ Диспетчер/Бригадир переводит статус
        ↓
  IN_PROGRESS  ← fact_start заполняется автоматически
        ↓
   CHECKING   ← Проверка качества
        ↓
      DONE    ← fact_finish заполняется автоматически
        ↓ (опционально)
  BOSS согласует → approved_by_boss = true
```

**Важно:** Диспетчер видит только заявки со статусом ≥ PLANNED (NEW скрыты).

## Панели

### Диспетчерская `/dispatcher`
**Роли:** DISPATCHER, ADMIN, BOSS

Центральный пульт смены. Видит все согласованные заявки в реальном времени.

- Канбан-доска с drag-and-drop (PLANNED → IN_PROGRESS → CHECKING → DONE)
- Таблица заявок с фильтрами по службе
- KPI-карточки: всего / в работе / выполнено / критических
- Статистика людей: сколько человек от каждой службы задействовано
- Сводка по службам: количество заявок на каждую
- Обновление каждые 30 секунд

---

### Зам/Прораб `/zamporab`
**Роли:** ZAMPORAB, ADMIN, BOSS

Планирование смены. Работает до 16:30 (таймер обратного отсчёта).

- Список заявок, ожидающих согласования (approved_by_head=true, не согласовано Зам/Прорабом)
- Кнопка «✓ Согласовать» → переводит заявку в PLANNED, она появляется у Диспетчера
- Заявки сгруппированы по службам
- Вкладка «Запросы людей»: межслужебные переводы сотрудников (StaffRequest)
- PlanStats: сколько заявок по каждой службе, сколько ждут решения

---

### Мастер/Бригадир `/foreman`
**Роли:** FOREMAN, ADMIN, BOSS, ZAMPORAB

Выполнение работ на месте.

- Мои задачи / Все задачи (фильтр по назначению через RequestAssignment)
- Кнопки: «Начать работу» (→ IN_PROGRESS), «На проверку» (→ CHECKING), «Готово» (→ DONE)
- fact_start и fact_finish заполняются автоматически при смене статуса
- Счётчики: всего / в работе / выполнено

---

### Начальник службы `/head`
**Роли:** HEAD, ADMIN, BOSS

Планирование работ своей службы.

- Создаёт заявки только для своей службы (service_id берётся из сессии)
- Назначает сотрудников своей службы на заявки (чекбоксы → RequestAssignment)
- Кнопка «Согласовать» → approved_by_head = userId → заявка уходит к Зам/Прорабу
- ServiceStats: всего / назначено / выполнено

---

### Дашборд Босса `/boss`
**Роли:** BOSS, ADMIN

Обзор и контроль всего.

- Health-индикатор (🟢/🟡/🔴):
  - 🟢 Зелёный: нет критических + >50% выполнено
  - 🔴 Красный: >3 критических заявок
  - 🟡 Жёлтый: всё остальное
- KPI: всего заявок, % выполнения, критических, ожидают согласования, людей в работе
- Графики: по статусам, по приоритету, по службам
- Вкладка «Согласование»: список заявок на финальное согласование Боссом
- Вкладка «Лог»: 30 последних действий в системе (changelog)

---

### Транспорт `/transport`
**Роли:** TRANSPORT, ADMIN, BOSS, ZAMPORAB

Управление автопарком.

Техника (захардкожена):
```
V-01  ГАЗель фургон
V-02  КамАЗ самосвал
V-03  УАЗ Патриот
V-04  Автовышка
V-05  Водовоз
```

- VehicleGrid: карточки техники с текущими назначениями
- TransportRequests: заявки, которым нужна техника (transport_type не назначен)
- Назначение: выбрать технику из дропдауна → обновляет поле transport_type в заявке

---

### Жалобы `/complaints`
**Роли:** COMPLAINTS, ADMIN, BOSS, DISPATCHER

Учёт обращений граждан.

- Форма регистрации: источник (телефон/ФИО/организация), описание, приоритет (LOW/MEDIUM/HIGH)
- Фильтры: все / новые / в работе / решённые
- Хранение: таблица `remarks` (request_id = 'COMPLAINT', remark_text = "источник|описание")

---

### Админ-панель `/admin`
**Роли:** ADMIN

Управление всеми справочниками.

Вкладки:
1. **Пользователи** — полный CRUD: таб.номер, ФИО, должность, роль, служба, телефон, PIN
2. **Службы** — SRV-ENG, SRV-STR, SRV-FIRE, SRV-VENT, SRV-CCTV
3. **Категории** — категории работ
4. **Объекты** — физические места с привязкой к категории
5. **Конструкции** — элементы внутри объектов
6. **Виды работ** — конкретные задачи внутри конструкций
7. **Лог** — 100 последних записей аудита (только чтение)

## Иерархия справочников

```
Категория
  └─ Объект (место)
      └─ Конструкция
          └─ Вид работы
```

Пример:
```
Инфраструктура тоннеля
  └─ Лефортовский тоннель (правая труба)
      └─ Дренажная система
          └─ Прочистка дренажных каналов
```

## Система смен

База: **2 января 2025 = Смена 4** (Станишевский А.В.)
Цикл: **1 рабочий день + 3 выходных** (4-дневный)

| Смена | Начальник смены | Таб. номер |
|-------|----------------|------------|
| 1 | Чекин А.В. | 0000-00001 |
| 2 | Максимов И.Н. | 0000-00002 |
| 3 | Кожин В.М. | 0000-00003 |
| 4 | Станишевский А.В. | 0000-00004 |

Периоды: **День** 07:00–19:00 ☀️ / **Ночь** 19:00–07:00 🌙 / **Сутки** 🌗 (график 1/3)

### Типы графиков сменности (эталон `SCHEDULES` в `src/lib/shifts.ts`)

| Код | Логика | Привязка к смене |
|-----|--------|------------------|
| 1/3 (сутки/3) | работает, когда дежурит его бригада | да — нужен `shift_num` |
| 5/2 | будни | да — `shift_num` + день недели |
| 3/3 | 3 через 3, скользящий цикл | нет — опорная дата |
| 6/6 | 6 через 6, скользящий цикл | нет — опорная дата |
| 15/15 | 1–15 / 16–конец месяца | нет — группа ротации '1'/'2' |

Часы и фазы (день/ночь/сутки) — эталон `SHIFT_HOURS` в `src/lib/workSchedule.ts`.
Ключевые функции: `isWorkerOnDuty(assignment, date)`, `resolveShiftForDate(assignment, date)`.

### Согласование план-наряда (`work_plans`)

Отдельный от `requests` поток: `DRAFT → SUBMITTED → APPROVED → REJECTED → PLANNED →
BOSS_CONFIRMED → ASSIGNED → IN_PROGRESS → DONE`. Цепочка: нач. службы (до 16:00) →
гл. инженер → зам → босс (совещание 16:30) → мастер формирует бригады пофамильно.

## Evolution

1. Требования опровергнуты? → в Out of Scope с причиной

1. Полный обзор всех разделов
2. Core Value — всё ещё верный приоритет?
3. Аудит Out of Scope — причины ещё в силе?
